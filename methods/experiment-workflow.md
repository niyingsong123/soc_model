# 模型开发与性能实验方法

本文件维护模型、实验和运行结果的组织方法。目录职责见 [项目入口](../README.md)，长期证据边界见 [AGENTS.md](../AGENTS.md)。

## 从一个可回答的问题开始

每个实验先明确问题、系统范围、比较变量和指标。例如，“在固定读写比例与访存延迟下，提高 DMA outstanding 上限是否提高有效拷贝带宽”，比“研究 SDMA 性能”更适合直接形成实验。

初次实验可以使用官方组件。只有现有组件无法表达所需行为、资源或观测量时，再扩展模型；说明增加的机制与要回答的问题之间的关系。

模型若用于说明原理，标明教学假设；若用于预测目标设计，标明参数来源与校准依据。尚未确定的目标事实不能通过默认值悄悄补齐。

## 文件职责与命名

实验采用 `E001-<topic>` 这类稳定标识。编号在首次建立实际实验时分配，不提前创建空目录。同一问题的参数扫描放在同一实验中，新的研究问题再建立实验；单次运行不等同于一个新实验。

| 位置 | 内容 |
| --- | --- |
| `models/<model>/` | 可复用模型及接口、参数、抽象和限制说明 |
| `configs/` | 可复用系统组成、地址范围、端口连接和默认参数 |
| `experiments/<experiment-id>/README.md` | 问题、方法、变量、验证依据、结果与结论 |
| 对应实验目录内的脚本和输入 | 参数扫描、workload、小型自建输入、运行与分析代码 |
| `runs/<experiment-id>/<run-id>/` | 一次运行的元数据、完整配置、统计、日志与必要 trace |
| `experiments/<experiment-id>/evidence/<run-id>/` | 支撑结论而选定保留的小型运行证据 |

`run-id` 应唯一，可采用带时区的时间与短参数名，例如 `20261011T180000+0800-linear-r100`。这是格式示例，不表示已有该次运行。脚本从参数取得本机路径，不把个人路径写死到可复用配置中。

## 接入官方构建与运行入口

保持官方 checkout 内部结构。构建从对应仓库的 `SConstruct` 进入，官方 `configs/` 和 `tests/` 保持原位；本项目模型和实验通过已有接口接入。

- 新增 C++ / SimObject 模型放 `models/<model>/`，使用该版本要求的 `SConscript`、`Source()` 和 `SimObject()` 注册源码与对象。官方构建传入 `EXTRAS=<本项目 models 的绝对路径>`；所需参数、头文件路径、对象名称和实际纳入构建的文件要在首次模型检查中验证。
- `EXTRAS` 用于增加代码，不自动替换已有 gem5 类的实现。修改官方已有代码时，按基线与 patch/开发 commit 管理，并在运行身份中记录。
- Python 实验入口可以位于外层实验目录；gem5 的 `--path` 将本项目模块路径加入 Python 搜索路径。配置中的 `m5.objects` 必须与实际编译得到的 SimObject 对应。
- `--outdir`、`--path` 是 gem5 自身参数，放在配置脚本路径之前；脚本自己的参数放在脚本之后。每次运行指定独立输出位置，避免落入当前目录下的默认 `m5out/`。

以下仅说明 Linux 中的接口连接方式，尚未执行；`SOC_MODEL_ROOT` 与 `GEM5_ROOT` 分别由实际研究目录和对应源码 checkout 设置。模型目录、`SConscript`、实验入口和运行标识在有实际内容时创建。示例使用 RISCV 和 `-j 2`，实际构建目标与并行度仍需按实验及宿主机资源确定。

```bash
cd "$GEM5_ROOT"
scons build/RISCV/gem5.opt EXTRAS="$SOC_MODEL_ROOT/models" -j 2

"$GEM5_ROOT/build/RISCV/gem5.opt" \
  --path="$SOC_MODEL_ROOT" \
  --outdir="$SOC_MODEL_ROOT/runs/E001-<topic>/<run-id>" \
  "$SOC_MODEL_ROOT/experiments/E001-<topic>/run.py"
```

接口依据：[官方 EXTRAS 说明](https://www.gem5.org/documentation/general_docs/building/EXTRAS)、本地选定版本的 `SConstruct`（EXTRAS 解析）、`src/SConscript`（外部源码遍历）和 `src/python/m5/main.py`（`--path`、`--outdir`、脚本执行）。确切源码基线见 [上游登记](../upstream/README.md)。这些源码核对不等同于本项目外部模型已完成编译验证。

## 一个实验正文应能回答的问题

正文按实际复杂度组织，至少包含以下内容；不需要为每一项另建管理文件：

1. **研究问题与范围。** 哪个机制是研究对象，哪些模块被抽象，结果适用于什么条件。
2. **模型与来源。** 所用组件、关键行为、版本、依赖、已知简化及参数依据。
3. **变量与对照。** 基线、扫描变量、保持不变的配置、workload、随机种子和重复运行策略。
4. **运行方法。** 构建与执行命令、输入身份、实际环境定位，以及对应的 run ID。
5. **指标与测量区间。** 单位、统计对象、起止条件、warm-up、是否 reset stats，以及多个统计区段的选取方法。
6. **验证与结果。** 实际执行的检查、数据与图表、异常和失败；预期与实测分别记录。
7. **解释与限制。** 变化来自哪个资源或阶段、证据是否支持该解释、尚未排除的原因，以及下一步需要回答的问题。

源码定位使用仓库、commit、文件与函数。学习笔记可以解释机制，实验正文引用该笔记，但关键参数和运行条件仍应能从该实验的证据恢复。

## 模型开始运行前的检查

先核对对象和端口是否真正连通、地址范围是否覆盖访问、ISA 与协议是否匹配，以及 Board 是否提供所需 I/O/DMA 接口。官方脚本能运行，不表示加入的新对象已经位于实际请求路径上。

对新增模型，根据实现范围检查：请求接纳与 retry、有限队列和 outstanding、读写数据正确性、返回关联、顺序和完成条件、异常及 drain 行为。解释每个时间参数的单位、起点和施加位置，检查研究路径中固定延迟、functional access 或绕过资源限制的行为。

测试选择应能发现实际错误。例如检查不同长度或边界上的搬运数据、资源已满后的拒绝与重试、完成通知是否过早，以及少量请求的可手算时序。文档整理不需要附加仿真测试；未改变的模型不因编辑说明而自动重跑全部测试。

## 每次运行保存什么

每次运行建立独立目录。开始记录、完成状态和失败原因都应落在该次运行内；被结论引用后保留其身份，新的配置或重试建立新的 run ID。

| 信息 | 记录要求 |
| --- | --- |
| 实验与运行身份 | experiment ID、run ID、起止时间与时区、状态、退出码；失败时保留错误信息 |
| gem5 身份 | 实际 commit、工作树是否有改动；有改动时保存可恢复的 patch 或开发 commit |
| 自建代码身份 | 本项目 commit；尚无 Git 或存在未提交改动时，保存相关源码/脚本快照与校验值 |
| 构建身份 | ISA、协议、构建目标、影响结果的选项、编译器和主要依赖版本、可执行文件身份 |
| 输入与配置 | workload 与资源版本/校验值、实际参数、随机种子、工作目录和完整命令 |
| 测量定义 | ROI、warm-up、停止条件、统计重置和输出区段选择 |
| 原始输出 | `config.ini`、`config.json`、`stats.txt`、标准输出与错误；实际生成什么就记录什么 |

可采用 `run.json` 保存运行元数据，配合原始文件；引入运行脚本时再固定机器可读格式，不先制造没有真实运行的记录。环境路径可以保存在本地文件，分享的实验仍需说明环境类型与足够的重建条件。

## 怎样形成可信的性能结论

验证分三层，按目标决定需要完成到哪一层：

| 层次 | 检查内容 | 能支持的结论 |
| --- | --- | --- |
| 功能与完成语义 | 数据正确、请求与返回对应、无丢失或重复、通知时点符合定义 | 模型在所检用例中正确完成指定操作 |
| 模型行为与性能约束 | 可手算时序、带宽上限、资源饱和、变量对照、必要的重复采样 | 模型中的机制与观测结果相符 |
| 目标校准 | 目标规格、RTL、microbenchmark 或硬件测量，以及误差分析 | 在已校准条件下预测目标设计 |

教学实验可以在明确前两层范围后完成；目标预测需要第三层依据。不能把对 gem5 参考实现的比较写成目标硬件验证。

统计统一说明时间、数据量和请求粒度。DMA 的有效拷贝带宽使用完成的有效拷贝字节数除以相应测量时间；它与总读写流量不是同一指标。对等待、服务与返回时延，需要考虑阶段重叠，不能把不独立的平均值机械相加。

比较实验尽量保持其他条件一致。涉及随机流量或不稳定统计时，根据问题安排重复运行并解释变化范围；不对所有确定性小实验机械规定固定重复次数。

## 原始输出与可审阅证据

`runs/` 默认保留在本地，不直接纳入项目 Git；用于正式结论的数据必须能通过正文中的 run ID 定位。

整理结论时，在对应实验的 `evidence/<run-id>/` 选择保留足以复核的小型元数据、配置、统计片段或分析输入；注明原始文件校验值、提取范围和提取方法，保留单位与统计区段。必要图表与生成脚本一并保留。选定证据是运行结果的固定摘取，不作为另一份可手工修改的运行记录。

大型 trace、disk image 或受限输入可以继续保留在其登记位置；说明获取或访问条件，不因存在图表就宣称别人已能独立复现。发布范围遵守用户授权及原始来源约束。

## 完成与接续

一个实验的完成包括实际运行、与研究目标相称的验证、可定位的证据和对结果的解释。只有配置或计划时写为“已准备”；只成功退出时写为“已运行”；验证完成再写明通过了什么检查，不合并成含义不明的“全部完成”。

结论写回该实验正文，项目级进度只记录阶段变化和入口。后续扩展保留旧 run ID 和适用条件；需要更改旧结论时说明新证据与影响范围。
